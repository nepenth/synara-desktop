# Desktop timeline, read-state, and room-activity audit

Audit date: 2026-07-21. Local baseline: [`main` at `5f78d08`](https://github.com/nepenth/synara-desktop/commit/5f78d08fb78672fbdc670c8fdd516a48bff28811). Review window: 2026-07-14 00:00 through 2026-07-21 23:59 America/New_York, using committer dates. There were no local commits on July 14–17 or July 20–21.

## Conclusions

- The reported failures shared two causes: UI-owned snapshots that were not subscribed to SDK changes, and timeline/read state split across independently mutating paths. The original desktop Recent implementation was a `useMemo` scan of `getLastActiveTimestamp()`. A room could be removed from the main list before a later render placed it in Recent. The original mark-as-read path wrote only a receipt, not the exact `m.fully_read` marker used by other clients.
- The seven-day history contains 34 commits: five product/runtime changes and 29 version, release, or workflow changes. The release churn repeatedly made validation, signing, build, artifact, and publication failures non-fatal. A successful workflow in this period therefore did not necessarily prove that every client or artifact was valid.
- The strongest upstream pattern is not a particular UI toolkit. Element Web, Element X iOS, and Cinny all separate live and event-focused timeline ownership, bound the displayed window, and restore a stable event plus pixel offset when the window changes. Element X additionally defers structural snapshots while drag or momentum is active.
- No inspected reference implements Synara's exact Recent (24h) product. The reusable part is the source of truth: Element Web prefers the Sliding Sync bump stamp and relevant timeline events; Element X consumes SDK room-list vector diffs and `latestEvent()` summaries. A wall-clock partition belongs on top of that reactive source, not on a one-time room scan.
- Synapse 1.157.0 can accept an explicitly backwards `m.fully_read` write under MSC4446, but the capability is experimental, disabled by default, and opt-in per request. Synara does not send that opt-in and keeps client writes monotonic. This is deliberate: navigating into history must never move another client's fully-read position backwards.
- The desktop fixes are mapped below. Exact marker writes and reactive room activity have direct unit coverage. Large-room scroll and Jump Latest have a deterministic browser regression harness, but production Matrix-backed, cross-client, and mounted-component tests remain mandatory before removing rollout controls.

## Synapse 1.157.0 and MSC4446

- The signed 1.157.0 tag resolves to `e0f251ce`; [release notes](https://github.com/element-hq/synapse/blob/e0f251ce2c0e20eff7af423c68ee349923f6d719/CHANGES.md#synapse-11570-2026-07-21) say there are no significant changes since RC1. Relevant client-facing changes include MSC4446 support; relevant server-performance changes include Sliding Sync lock/index fixes and presence traffic/timer work.
- [Upgrade notes](https://github.com/element-hq/synapse/blob/e0f251ce2c0e20eff7af423c68ee349923f6d719/docs/upgrade.md#upgrading-to-v11570) require deployments using deprecated `experimental_features.msc3861` auth delegation to migrate to stable Matrix Authentication Service configuration. This must be checked in deployed configuration; this repository audit had no server-config access.
- [Synapse PR 19663](https://github.com/element-hq/synapse/pull/19663), merge commit `bf0f4f6a9dcc14f92f1a1256ad64755b373bfded`, implements the still-open [MSC4446 proposal](https://github.com/matrix-org/matrix-spec-proposals/pull/4446). `experimental_features.msc4446_enabled` defaults false. When enabled, the server advertises `com.beeper.msc4446`; a client must additionally send `"com.beeper.allow_backward": true`, and only for `m.fully_read`. Without that field, the existing forward-only server comparison remains in force.
- Synara should not send `com.beeper.allow_backward` from ordinary timeline navigation, Jump Latest, Recent, or mark-as-read. Its per-room queue serializes combined marker writes and discards/coalesces older targets. Backwards movement could become a separate, explicit future product action, guarded by capability discovery and user intent, but it is not a recovery mechanism for stale clients.
- Operators should verify the running version through `/_synapse/admin/v1/server_version`, read every intervening upgrade note, monitor database background updates, and verify PostgreSQL/Python support as directed by the [official upgrade guide](https://element-hq.github.io/synapse/v1.157/upgrade.html). Nothing found justifies server-side history purges, database changes, or wider timeline limits as a fix for client viewport jumps.

## Accepted and rejected patterns

Accepted:

- SDK ownership for live and event-focused timeline contexts, with explicit transitions between them.
- A bounded displayed window independent of message height; event ID plus measured pixel offset is the anchor.
- No structural snapshot or scroll writes during active drag/wheel momentum; apply queued changes after idle.
- Jump Latest reloads/rebinds the true live tail, survives errors, and hides only after bottom confirmation.
- Relevant-event activity driven by live SDK events and bump stamps, with one atomic, disjoint Recent/non-Recent partition and scheduled 24-hour expiry.
- Exact combined `setRoomReadMarkers` writes, per-room serialization, monotonic coalescing, receipt privacy selection, and clearing custom unread state only after server success.
- Bounded, content-free diagnostics and default-on emergency rollback switches during rollout.

Rejected:

- `useMemo` plus `Date.now()` and `getLastActiveTimestamp()` as a reactive activity store.
- Removing a room from one UI collection before its membership in the other is derived from the same snapshot.
- Treating scroll-to-DOM-bottom in an old/focused window as reaching latest.
- Repeated pagination through an arbitrarily old marker, or allowing a stale marker to override an explicit deep link or fresh live-end state.
- Index-only/fixed-height restoration for variable-height encrypted messages, images, replies, edits, or fonts.
- Applying pagination/layout corrections while the user has active scroll momentum.
- Independent receipt and fully-read promises, read-on-room-leave, or any implicit backwards fully-read write.
- Unbounded DOM/timeline growth as the large-room performance strategy.
