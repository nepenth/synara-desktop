## Summary

- Flow kinds: Login | Registration | PasswordReset | StepUp
- Stage kinds mapped from `m.login.*` (password, recaptcha, email, msisdn, terms, dummy, registration_token; other types are `Unknown`)

## Out of scope

- SDK UIA network submit
- Password/captcha/code storage
- Production Tauri commands, dual-backend
- Desktop SSO/OAuth authentication, callback, and SSO UIAA continuation

## Current V-AUTH.1 desktop boundary

`m.login.sso` maps to `Unknown`; this coordinator has no SSO stage or
continuation. The desktop therefore offers no SSO UI or SSO UIAA support, and an
SSO-only UIAA response is unsupported. Native other-device deletion retains its
separate password-only UIAA path when a viable password-only flow is offered.
The OIDC account-management dashboard remains an external account-management
route, not an SSO UIAA mechanism. Desktop `m.login.token` product login is not
retained (**V-AUTH.2**); this UIA coordinator remains independent of that closed
decision.

## V-AUTH.3b login multi-stage boundary

Product **login** does not retain multi-stage UIA (see
[v-auth-3b-uia-login-stage.md](v-auth-3b-uia-login-stage.md)). Password login is
single-shot `matrix_login_password`; a homeserver UIAA challenge on login fails
closed as `InteractiveAuthRequired` rather than driving a product stage UI.
Multi-stage product UIA remains on **register** (native #266) and password-reset
chrome (#263); device-delete keeps password-only UIAA. This P3.4 harness is
**not** product-wired as generic `matrix_uia_*` login-stage IPC.
