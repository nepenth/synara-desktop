# D0.1 — Rust password-login sole owner

## Outcome

Desktop password login is owned by the Tauri host and `matrix-sdk`. The WebView
does not create a `matrix-js-sdk` client or issue `loginRequest` for a desktop
password session. Browser builds keep the existing JavaScript login path.

This is a deliberately breaking cutover. Rooms, timelines, sync, and other
post-login product state remain for D0.2 and later.

## Native command surface

The Tauri invoke handler registers:

- `matrix_login_password(homeserverUrl, user, password)` — builds the native
  client, logs in, persists the native session, and returns only `userId`,
  `deviceId`, and `homeserverUrl`.
- `matrix_session_snapshot()` — returns `logged_out` or the non-secret live
  identity.
- `matrix_logout()` — logs out through `matrix-sdk`, clears the session vault
  entry and active identity descriptor, and drops the managed client.
- `matrix_restore_session()` — reads the non-secret active identity descriptor,
  opens that account's native store, restores its keyring session material, and
  installs the client as the managed live client. A missing descriptor or vault
  entry produces an explicit error.

The command return and error types contain no access token, refresh token,
password, or sealed vault bytes.

## Ownership and persistence

`MatrixAuthState` holds at most one live `matrix_sdk::Client` behind an async
mutex. Client construction continues to go through
`matrix::client_builder::build_unauthenticated_client`.

Store keys use `KeyringStoreKeyVault`. Login session material uses
`matrix::lifecycle::persist_session_after_login` and
`KeyringSessionMaterialVault`; restore uses
`matrix::lifecycle::restore_session_from_vault`.

`{app_data}/matrix/active-session.json` is a non-secret restore pointer. It
contains only the user ID, device ID, and homeserver URL needed to select the
account-scoped native store and vault entry. Tokens never enter this file or an
IPC response.

## Product routing

`PasswordLoginForm` calls `loginPassword`. When the Tauri bridge is present,
that function invokes `matrix_login_password`; it does not fall through to
`createClient` or `loginRequest`. A native success navigates through the
existing completion hook without persisting a JavaScript/service-worker
session.

The `matrix-js-sdk` login helper remains for browser password login and the
currently out-of-scope token/SSO path. It does not own the same desktop password
session.

## Known D0.1 breaks and limits

- The desktop command requires a full Matrix user ID so the correct
  account-scoped encrypted store can be opened before login. The username form
  expands a localpart to `@localpart:server`; third-party email identifiers
  receive an explicit invalid-request error on desktop in this slice.
- No native sync, room list, timeline, or JavaScript client hydration starts
  after login. The post-login UI may therefore be incomplete or broken until
  D0.2.
- SSO, token login, and UIA polish are unchanged and out of scope.
- Native durable login/restore requires a supported and available OS credential
  store. There is no WebView token fallback.
