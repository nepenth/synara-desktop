## Executive summary

This task implements **password login + generic token foundation + platform device naming**
(plan Phase 3 / P3.2, FR-7.1-011 + login path of FR-7.1):

- Password login via `Client::matrix_auth().login_username(...).initial_device_display_name(...).send().await`
- Generic one-time-token login foundation via `Client::matrix_auth().login_token(...).initial_device_display_name(...).send().await`
- Platform device display names per **D-NEW-DEVICE**: `Synara macOS` / `Synara Linux` (desktop fallback `Synara Desktop`)
- Privacy-safe `AuthError` extensions for login failures (no password/token echo)
- Guardrail allowlist: `.login_username` / `.login_token` / `.matrix_auth(` **only** under `src-tauri/src/matrix/auth/`
- Unit tests for validation, device names, error privacy, and classifier mapping

**Out of scope:** production Matrix Tauri login/sync commands, dual-backend,
desktop SSO/OAuth callback support, UIA stage machine (**P3.4**), refresh-token
persistence (**P3.5**), session restore (**P3.6**), legacy transition coordinator
(**P3.7**), elaborate JS→Rust token/device migration (clean-break approved).

Product Matrix runtime remains **only** `matrix-js-sdk` until planned cutover.

## Current V-AUTH.1 desktop boundary

- The desktop login screen offers **password login only**. It has no SSO UI,
  callback, popup, or SSO UIAA continuation.
- An SSO-only login response is unsupported. A generic `m.login.token` model
  and host-side foundation remain, but no desktop token-login route is exposed;
  any product exposure requires an explicit **V-AUTH.2** decision.
- Password UIAA remains available for native other-device deletion when the
  homeserver offers a password-only viable flow. SSO-only or mixed flows that
  still require SSO are unsupported there as well.
- The OIDC account-management dashboard (including its session-management
  actions) remains an external dashboard route, not desktop SSO authentication.

## 2. Module surface

| Item | Role |
|------|------|
| `login_with_password` | Password login on unauthenticated P2.3 `Client` |
| `login_with_token` | Generic one-time login-token foundation (not an access token); not exposed by the desktop UI pending V-AUTH.2 |
| `LoginOptions` | Device display name override + optional `request_refresh_token` flag |
| `LoginResult` | Privacy-safe identity outcome (user/device/hs/name/method) — **no tokens** |
| `platform_device_display_name` | Host platform product device name (D-NEW-DEVICE) |
| `AuthError::{AuthenticationRejected,UserDeactivated,InteractiveAuthRequired,RateLimited}` | Login failure categories |

## 3. Device naming (D-NEW-DEVICE)

| Platform | Display name |
|----------|--------------|
| macOS | `Synara macOS` |
| Linux | `Synara Linux` |
| iOS (shared table) | `Synara iOS` |
| Other desktop targets | `Synara Desktop` |

Login always sets `initial_device_display_name` to the resolved product string
unless an explicit `LoginOptions.device_display_name` override is supplied
(harness/tests only).

---

## 4. Privacy

- `LoginResult` never includes `access_token` / `refresh_token` / password / login token.
- Tokens remain on the live SDK `Client` after success (host-side only).
- `AuthError` Display/debug carries only static diagnostic ids and privacy-safe reasons.
- Guardrails continue to ban `restore_session` / sync APIs under `matrix/`.
