The accepted local design provides:

- closed JSON schemas for normalized audit input and traceability v2;
- deterministic check, generate, and baseline-migrate command entry points;
- immutable source and cutover projections for requirements, blockers, and
  architecture decisions;
- append-only validation-report, execution, entity-chain, and lifecycle-
  authorization history;
- exact source, baseline, transition, predecessor, self, report, subject, and
  reviewer/time/rationale digest bindings;
- authorized creation of new blockers and architecture decisions without
  allowing historical source entities to be rewritten;
- risk, decision, readiness, closure-evidence, and rollback semantics;
- Git-derived immediate prior-v2 discovery on the first-parent path;
- validation of previous artifacts before accepting append-only evolution;
- historical execution-contract snapshots separated from current evidence;
- bounded, isolated performance checks and adversarial real-Git regressions.

## Review and correction history

Most of the elapsed effort was review, falsification, and correction rather than
initial code entry. That was necessary because early drafts could pass ordinary
happy-path tests while failing the program-long evidence model.

The review loop identified and required correction of these material defects:

- one-shot authorizations that could not represent multi-step program history;
- lifecycle reports and authorizations that could be replaced or truncated;
- risk and architecture-decision states that could not evolve or close safely;
- historical source evidence that could disappear at a later commit;
- insufficient separation between immutable source projections and mutable
  lifecycle snapshots;
- incorrect ancestry semantics that rejected a legitimate newer-commit rollback;
- created entities losing their original source payload after sequence one;
- planned-state test fixtures retaining execution contracts that should be null;
- obsolete one-shot compatibility paths remaining reachable;
- prior-v2 artifacts being compared without first proving schema and semantic
  validity;
- a history-search bound that limited commits rather than path-changing versions;
- benchmark behavior sensitive to shared-process memory rather than isolated RSS;
- missing real-Git coverage for truncation, fork/merge, subject ancestry, report
  storage order, and historical artifact evolution.

The resulting implementation is substantially stronger than the first draft.
The cost was high iteration count and low apparent feature throughput.

E1 intentionally validates pinned commits and prior path history. The existing
desktop-validation checkout was shallow, so GitHub Actions could not read pinned
commit `2aa6d96…`. This was an environmental incompatibility in CI, not a reason

PR #83 made the validation checkout fetch full history. It targeted the

was kept out of E1’s strict 11-path scope.

### Refreshed E1 CI: Git author portability

PR #82 was refreshed on the new integration base without changing its accepted
11-file content. CI progressed through the history checks and ran 284 repository
script tests. It passed 283.

The sole failing test path uses `temporaryLocalGitClone`, then commits fixture
history without configuring a local Git author. A developer environment supplied
an identity during local validation; the GitHub runner correctly had none. The
fix is to configure repository-local `user.name` and `user.email` inside that
helper before the first commit. It must not change production code, schemas,
assertions, or Git-history semantics.

The CI job accounting was:

- `Quality gate`: failed downstream because desktop validation failed;
- `iOS simulator tests`: passed;
- `Synapse two-client integration`: passed;
- macOS app bundle: passed;
- Linux `.deb` and Arch packages: passed;
- desktop package gate: passed.

Therefore PR #82 must not merge yet, despite its Git-level mergeability and local

## Honest workflow assessment

### Quality

The review process produced high-quality corrective tooling. It found multiple
false-green designs that ordinary unit coverage did not expose and required
program-long, append-only semantics with real Git evidence. Scope discipline was
strong: production work stayed inside 11 paths, the CI prerequisite used a
separate PR, no dependency/runtime drift entered, and nothing reached integration
without the required review boundary.

### Throughput

Throughput was poor relative to elapsed time. E1 consumed many correction rounds,
and most visible work was test, validator, schema, and evidence infrastructure
rather than user-facing Rust SDK replacement. The initial task was too large:
thousands of lines combined two schemas, a lifecycle engine, Git-history
semantics, generators/migration, performance bounds, and extensive adversarial
tests. Important invariants were discovered during review instead of being fully
specified before the first implementation pass. That caused expensive rewrites.

CI also exposed two environment assumptions late: shallow Git history and test
commits without a local author. Both are legitimate portability findings, but
they should have been included in the original task packet and reproduced in a
clean CI-like local environment sooner.

### Recommended process adjustment

For subsequent work:

- split normative model/schema, implementation, real-Git integration, and
  artifact-generation work into smaller prerequisite slices;
- define lifecycle transition tables and append-only history authority before
  code generation begins;
- run tests with isolated `HOME`, no global Git identity, and CI-equivalent clone
  depth during the first correction round;
- keep one implementer responsible for a bounded slice while a separate reviewer
  attacks it with explicit negative cases;
- reserve full repository and package validation for logical checkpoints, while
  still requiring the complete gate before merge;
- report R0 remediation separately from original feature progress so governance
  work is visible without suggesting the SDK cutover advanced.
