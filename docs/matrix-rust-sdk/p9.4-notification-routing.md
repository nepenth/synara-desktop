# P9.4 — Room / event / thread notification routing

Status: pure Rust harness foundation. The product runtime remains
`matrix-js-sdk`; `dual_backend=false`.

## Scope

`matrix::notification_routing` resolves privacy-safe notification candidate
fields into an internal destination and retains the last resolved route for each
opaque candidate key.

- `NotificationRouteKind`: `Room`, `Event`, or `Thread`.
- `NotificationRoute`: room id, optional event id, optional thread-root id, and
  resolved kind.
- `NotificationRouter`: validates identifiers, resolves destination specificity,
  records the last route by candidate key, and clears all routes when a session
  generation retires.
- `resolve_candidate` accepts a P7.1 `NotificationCandidate` and an optional
  thread root. The router does not consume its title, body, or prebuilt route.

Resolution precedence is thread root, event anchor, then room. A thread route may
also preserve an event anchor so a caller can focus a particular reply inside
the thread.

## Validation and privacy

Room ids must use the `!localpart:server` shape. Event and thread-root ids must
be non-empty and start with `$`. Candidate keys must be non-empty.

Routing values contain identifiers only. Errors retain and render static
diagnostic ids, never invalid caller input. This module has no notification
content DTO, logging, tokens, secrets, recovery keys, event plaintext, or media
bytes.

## Lifecycle

The registry is generation-stamped. `retire_generation(new_generation)` updates
the generation and wipes all routes from the retired session. No state is
persisted and no JS-to-Rust session migration is attempted.

## Explicitly excluded

- OS or desktop notification delivery
- push-rule network access
- production Tauri commands
- backend selection or cutover
- changes to program status
