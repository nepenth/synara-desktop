## Executive summary

This task implements **refresh-token / session secret persistence and rotation
structure** for the Matrix Rust foundation (plan Phase 3 / P3.5):

- Sealed v1 session envelope (access + optional refresh + identity metadata)
  stored **only** in `SessionMaterialVault` (host-side)
- Distinct keyring service from store encryption keys
  (`…matrix-session` vs `…matrix-store-key`)
- In-memory vault for unit tests; keyring-backed vault for production platforms
- Optional post-login hook: `persist_session_after_login(client, identity, vault)`
- Rotation path: same `SessionMaterialId`, overwrite blob via
  `rotate_persisted_session_tokens` / `persist_session_material`
- Privacy: tokens never on `LoginResult`, `SessionSnapshot`, IPC DTOs, logs, or
  error Display/Debug of public types

**Out of scope:** production Matrix Tauri commands, dual-backend, SSO (P3.3),
UIA (P3.4), **session restore** (`Client::restore_session` — P3.6), legacy
migration (P3.7), JS→Rust token migration (clean-break approved).

Product Matrix runtime remains **only** `matrix-js-sdk` until planned cutover.

## 3. Sealed envelope (v1)

JSON payload (UTF-8) stored in the vault:

```json
{
  "v": 1,
  "kind": "matrix",
  "user_id": "@alice:example.org",
  "device_id": "DEVICEID",
  "homeserver_url": "https://matrix.example.org",
  "access_token": "<TOKEN>",
  "refresh_token": "…" 
}
```

- `refresh_token` omitted when absent
- Version check rejects unknown `v`
- Placeholder blobs (non-JSON harness leftovers) remain loadable for wipe tests
  but product/login path always uses `from_matrix_tokens`

---

## 4. Post-login composition

```text
login_with_password / login_with_token  (P3.2)
  → SDK Client holds session tokens
  → LoginResult (privacy-safe identity only)
  → optional: persist_session_after_login(client, identity, vault)
       → client.session() → AuthSession::Matrix
       → bind user_id to AccountIdentity
       → seal envelope → vault.set(SessionMaterialId)
```

Login APIs remain free of vault coupling; callers compose the optional persist
hook. OAuth sessions are rejected with a privacy-safe diagnostic until a later
envelope lands with P3.3.

---

## 5. Rotation structure

When the SDK refreshes tokens (future product path):

1. Obtain new access (+ optional new refresh) host-side
2. Call `rotate_persisted_session_tokens(vault, identity, device_id, access, refresh)`
3. Same `SessionMaterialId` is overwritten — no dual-backend, no second account key

Live SDK `refresh_access_token` wiring remains product/cutover work; this task
only provides the vault overwrite structure.
