## Executive verdict

The handoff correctly reported a clean, synchronized integration branch and no
production cutover. It did **not** correctly report phase completion or readiness
to begin P3.2.

Twenty of the original 112 named task artifacts have landed: P0.1–P0.7,
P1.1–P1.6, P2.1–P2.6, and the P3.1 foundation. That is an implementation
inventory, not an acceptance result. On the plan's actual phase gates:

- Phase 0 is open because required cross-platform and live baseline evidence is
  explicitly residual, feature traceability is incomplete outside the
  notification/E2EE/search/call audit band, and mandatory planning artifacts
  were absent before Phase 2 started.
- Phase 1 is open because formatting, lint, and clippy gates fail; the IPC
  contract has unsafe cross-language integer and stream-identity semantics; and
  CI was not green before the task PRs merged.
- Phase 2 is open because native keyring integration and live lifecycle/crash
  tests are absent, and the review found blocking wipe-ordering, store
  confinement, and diagnostic-privacy defects.
- P3.1 has useful discovery/login-flow domain logic and mock tests, but its live
  SDK adapter and disposable-homeserver acceptance tests remain deferred.

Accordingly, **zero of 15 strict phase gates are closed**. P3.2 is blocked until
the remediation workstream below is accepted. The shipping product remains
`matrix-js-sdk`-only and there is still no dual backend or production cutover.

## Code-review findings

### REV-001 — local wipe deletes an account store before its owner is stopped

Severity: **Critical** (data loss / lifecycle race)

`perform_local_wipe` enters `Wiping`, deletes the store and key, then clears
session material, completes the wipe, and only afterward retires generation-
stamped tasks. The Matrix client/store handle and background tasks can therefore
remain live while their SQLite tree is removed. An open handle can race writes
against deletion, and a session-vault failure after deletion returns early with
the supervisor stuck in `Wiping`, live tasks retained, and data already gone.

Required correction:

1. Transition to a quiescing/wiping state that rejects new work.
2. Cancel and join all generation tasks.
3. drop the Matrix client and close every store handle;
4. clear session/key material and remove the exact account store under an
   explicit, recoverable partial-failure policy;
5. always leave the supervisor in a deterministic terminal/recoverable state;
6. add order-sensitive and injected-failure tests, including vault failure.

Affected code: `src-tauri/src/matrix/lifecycle/logout.rs:89` and lifecycle tests.

### REV-002 — store creation follows symlinks outside the app-data boundary

Severity: **High** (filesystem confinement / account isolation)

`StorePaths::derive` performs only lexical prefix checks. `ensure_dirs` then
uses `create_dir_all` and `set_permissions` on any pre-existing path, following
symlinks. A symlink at the matrix root, account root, or child store path can
cause store creation/open and permission changes outside the approved app-data
root. Relative app-data roots are also accepted. Wipe has a partial symlink
defense, but open/create does not.

Required correction: require an absolute trusted app-data root; use symlink-
aware component validation and canonical containment; refuse symlinks at every
managed component; create with safe permissions without traversing an attacker-
controlled link; add Unix symlink and relative-root tests for open and wipe.

Affected code: `src-tauri/src/matrix/store/paths.rs:78` and
`src-tauri/src/matrix/store/paths.rs:135`.

### REV-003 — values labelled privacy-safe disclose URLs and absolute paths

Severity: **High** (privacy / diagnostic disclosure)

`ClientBuildPlan` serializes the full homeserver URL and a `StoreLayout` with
absolute account, state, crypto, cache, and media paths. SDK build errors are
copied verbatim into error messages and may contain filesystem, homeserver, or
proxy values. `WipeReport` also exposes the absolute wiped path. These values
contradict the plan's no-secret/no-sensitive-path diagnostic requirement and
their own “privacy-safe” comments.

Required correction: diagnostics must expose bounded enums, booleans, stable
non-user identifiers, and redacted categories—not URLs, absolute paths, raw SDK
errors, user IDs, access tokens, or proxy data. Add explicit adversarial
redaction tests for paths, URL credentials/query strings, tokens, and SDK errors.

Affected code: `src-tauri/src/matrix/client_builder/config.rs:218`,
`src-tauri/src/matrix/client_builder/open.rs:72`,
`src-tauri/src/matrix/store/paths.rs:66`, and
`src-tauri/src/matrix/lifecycle/wipe.rs:79`.

### REV-004 — IPC counters are not safe across the Rust/JavaScript boundary

Severity: **High** (protocol correctness)

Rust encodes session generations and sequence counters as `u64`; TypeScript
uses `number` and accepts any number, including NaN, infinities, fractions,
negative values, and integers above `Number.MAX_SAFE_INTEGER`. Valid Rust `u64`
values can therefore silently lose precision in JavaScript. Rust sequence
checking also evaluates `last + 1`, which overflows at `u64::MAX` in debug and
wraps in release.

Required correction: choose and document one wire representation. Prefer a
bounded non-negative safe integer with checked increments, or decimal strings
with strict parsers. Enforce the same range in Rust, TypeScript, schemas,
fixtures, constructors, and property/boundary tests.

Affected code: `src-tauri/src/matrix/ipc/protocol.rs:34`,
`src-tauri/src/matrix/ipc/envelope.rs:88`, and
`synara/src/app/features/matrix-ipc/envelope.ts:71`.

### REV-005 — stream identity and payload contracts are ambiguous

Severity: **High** (stale/misrouted state; IPC trust boundary)

The envelope's `streamId` is optional while several stream payloads also carry
their own stream ID. Parsing does not require stream IDs for stream-scoped
messages or enforce equality when both exist. Snapshot/delta bodies remain
`serde_json::Value` / `unknown`; the domain DTO work is not bound to topic-
specific stream bodies, and payload-size/secret/media-byte restrictions are not
enforced at this parser boundary.

Required correction: establish a single authoritative stream identifier;
validate kind-specific required fields; bind every supported topic to typed,
bounded DTO bodies; reject mismatches, oversized bodies, secret-like fields,
and byte-array media payloads; add Rust/TypeScript golden and adversarial tests.

Affected code: `src-tauri/src/matrix/ipc/envelope.rs`,
`src-tauri/src/matrix/ipc/stream.rs`, and
`synara/src/app/features/matrix-ipc/envelope.ts`.

### REV-006 — the declared store layout does not match the SDK builder

Severity: **Medium** (design/evidence accuracy)

The layout allocates a dedicated `crypto_dir`, but
`sqlite_store_with_cache_path(state_dir, cache_dir, ...)` uses the SDK's state
directory for state and crypto storage and only separates the cache directory.
`crypto_dir` and `media_dir` are not consumed by the client builder. Comments
and task evidence overstate what is opened.

Required correction: either redesign the layout around the exact 0.18 API, or
document and test the actual state/crypto/cache ownership. Remove unused managed
directories unless another accepted owner is defined.

Affected code: `src-tauri/src/matrix/client_builder/open.rs:14` and
`src-tauri/src/matrix/store/paths.rs:55`.

### REV-007 — account-directory collision claims are too strong

Severity: **Medium** (account isolation)

Account isolation currently depends on an unkeyed 64-bit FNV-1a fingerprint,
described as providing collision resistance. That is not an appropriate claim
or primitive for an adversarial account-isolation boundary.

Required correction: use a collision-resistant digest of the normalized
identity (for example SHA-256 with a versioned derivation format), retain enough
bits for the threat model, and specify migration/versioning before any real
stores exist.

Affected code: `src-tauri/src/matrix/store/identity.rs:80`.

### REV-008 — quality gates and task records are not trustworthy yet

Severity: **High** (delivery control)

Rust formatting and strict clippy fail; TypeScript lint and Prettier fail; the
integration range contains trailing whitespace; and the final integration CI
run failed. Some machine-readable task records still say `in_progress` or
`accepted_pending_integration_merge` after merge. Repeatedly cancelled CI runs
were treated as sufficient to merge.

Required correction: fix all introduced formatting/lint failures; classify and
baseline genuinely pre-existing clippy findings without relabelling new ones;
make every task PR wait for required green checks; prevent the umbrella PR from
cancelling task validation; and reconcile Markdown/JSON task status with strict
acceptance rather than merge state.

### REV-009 — mandatory planning and live-evidence gates were bypassed

Severity: **High** (requirements/process)

The plan required, before Phase 2, a security/threat model, a test matrix and
disposable-Synapse topology, a review-report template, and a risk register with
owners/status. Those dedicated artifacts do not exist. P0.5 and P0.6 explicitly
retain cross-platform and live-measurement residuals. P3.1 supplies mock
transports but defers the live SDK adapter despite its integration acceptance
criteria.

Required correction: create and review the missing artifacts, close or formally
re-scope every residual, complete all feature-traceability rows to the promised
depth, and run the live disposable-homeserver acceptance path before P3.2.

## Branching and review protocol from this point

- Every remediation or original task starts from the latest integration tip on
  a `matrix-rust/<task-id>-<slug>` branch and targets only
  `feature/matrix-rust-sdk-full-replacement`.
- The orchestrator owns scope, Git/PR state, acceptance decisions, and the final
  diff review. Implementation agents receive a bounded task with exact files,
  requirements, forbidden changes, commands, and stop conditions.
- An implementation agent does not merge, broaden scope, waive failures, or
  reinterpret acceptance criteria. Findings are returned for correction on the
  same task branch until the entire diff meets the task gate.
- A task may merge only after independent review, required local validation,
  and a green, non-cancelled CI run on the reviewed SHA.
- PR `#39` must not merge to `main` without explicit user approval.
