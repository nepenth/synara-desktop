## Executive summary

This task implements the **discovery and login-flow service foundation** (plan
Phase 3 / P3.1, FR-7.1-001 + FR-7.1-005):

- Homeserver URL + Matrix server-name input normalization/validation
- Well-known discovery behind mockable [`DiscoveryTransport`]
- Login-flow listing behind mockable [`LoginFlowTransport`]
- Product-aligned **IGNORE** fallback when well-known is absent (404 →
  `https://{server_name}` base URL)
- Stable Synara domain types (`LoginFlowKind`, `LoginFlow`, `DiscoveryResult`)
  — no raw SDK/Ruma types on the module boundary
- Thin bridge into P2.3 `AccountIdentity` / client-builder homeserver URL
- Unit tests with in-memory mocks only (no live homeserver network)

**Out of scope:** password/token login (**P3.2**), SSO/OAuth callback (**P3.3**),
UIA/registration (**P3.4**), refresh-token persistence (**P3.5**), session
restore (**P3.6**), production Matrix Tauri commands, dual-backend, live SDK
`matrix_auth().get_login_types()` adapter (deferred residual — harness transport
is intentionally mockable).

Product Matrix runtime remains **only** `matrix-js-sdk`.

## 3. Discovery model (FR-7.1-001)

```text
parse_discovery_input(raw, prefer_ambiguous?)
  → DiscoveryInput::{HomeserverUrl | ServerName | ServerNameOrUrl}

discover_homeserver(input, DiscoveryTransport)
  HomeserverUrl     → normalize only (no network)
  ServerName        → GET well-known
                      • success → base_url from m.homeserver
                      • WellKnownNotFound (404 IGNORE) → https://{server}
                      • connectivity/unavailable → error (no silent fallback)
  ServerNameOrUrl   → try server-name well-known first;
                      URL fallback when input has scheme, or IGNORE on 404
```

Product parity notes (vs `synara/src/app/cs-api.ts` `autoDiscovery`):

| Product action | P3.1 mapping |
|----------------|--------------|
| `PROMPT` / success with `m.homeserver.base_url` | `used_well_known: true` |
| `IGNORE` (404 / missing well-known) | `AuthError::WellKnownNotFound` → `https://{server}` |
| `FAIL_PROMPT` / `FAIL_ERROR` | `UnsupportedCapability` / `InvalidInput` / `HomeserverUnavailable` |

## 5. Transport isolation (no live network in unit tests)

```rust
trait DiscoveryTransport {
    async fn fetch_well_known(server_name) -> Result<WellKnownClientConfig, AuthError>;
}

trait LoginFlowTransport {
    async fn fetch_login_flows(homeserver_base_url) -> Result<Vec<LoginFlow>, AuthError>;
}
```

- Production SDK adapter (well-known via `ClientBuilder::server_name*` /
  `matrix_auth().get_login_types`) is a **residual** for a follow-up once
  guardrails allow scoped discovery-only `matrix_auth` under `auth/` or a
  dedicated adapter module. P3.1 ships mock + domain service only.
- **No** `Client::builder` outside `client_builder/`
- **No** `login_username` / `login_token` / `restore_session` / `sync_*`

## 6. Privacy

- Errors carry only `diagnostic_id` + stable `MatrixIpcErrorCategory`
- Display/Debug never include tokens, passwords, Bearer headers, or recovery keys
- Domain types do not hold access/refresh tokens
