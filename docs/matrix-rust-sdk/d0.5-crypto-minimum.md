# D0.5 crypto minimum

## Dogfood decision

Encrypted rooms are enabled for native Rust sessions. There is no
unencrypted-only gate in this slice.

The production password-login and restore paths build one Matrix Rust SDK
client with `EncryptionSettings::default()` and the account-scoped encrypted
SQLite state/crypto store. Both SDK authentication paths activate the Olm
machine. Synara now verifies that the managed client has an active crypto
machine before starting native sync; if it does not, native login/restore fails
closed with a privacy-safe error instead of presenting a partially usable
session.

## What works

- Native sync supplies to-device crypto traffic and room events to the same
  managed SDK client.
- The SDK UI timeline decrypts events when room keys are available and retries
  late decryption when keys arrive. Synara projects the decrypted message body.
- Truly undecryptable events remain the fixed `Unable to decrypt this message`
  placeholder. Ciphertext and encrypted event content are never returned over
  IPC.
- `matrix_send_text` continues to call `Room::send` on the managed client. In an
  encrypted room the SDK establishes/shares the required Olm/Megolm sessions
  and encrypts the event; Synara does not implement a second crypto or send
  stack.
- `matrix_crypto_status` returns only the session generation, whether the SDK
  crypto machine is active, and a coarse cross-signing state
  (`unavailable`, `not_set_up`, `partial`, or `ready`). It returns no tokens,
  keys, ciphertext, passphrases, or recovery material.
- Native timeline snapshots include the room encrypted flag, and the desktop
  timeline identifies encrypted rooms and whether native crypto readiness was
  confirmed. Native sessions do not initialize matrix-js-sdk crypto.

## Residual work (blocking — full vertical policy)

**Superseded as acceptance.** Under [full-vertical-policy.md](full-vertical-policy.md),
this “crypto minimum” is **not** a completed crypto vertical. Outstanding product
work is tracked as **V-CRYPTO.\*** in
[d0-residual-completion.md](d0-residual-completion.md) and must be fully
re-implemented before new verticals proceed:

- device-verification UX
- key-backup restore UI
- interactive key-share prompts
- unable-to-decrypt recovery controls
- secret storage (SSSS) bootstrap/import UI
- device list / trust presentation on native session

V-CRYPTO.1–.4 now have merged native product wiring (#223–#226), and
V-CRYPTO.5 is active in draft #227. They are not closed under the clarified
[physical-deletion rule](full-vertical-policy.md): superseded JS crypto
implementations/imports must be removed in the owning vertical. The current
deletion and remaining crypto order is authoritative in
[d0-residual-completion.md](d0-residual-completion.md).

History whose keys are not already in the local Rust crypto store or delivered
by another device may stay undecryptable until V-CRYPTO recovery paths land.
Cross-signing can be absent or partial without blocking current room decryption
and encrypted sends until V-CRYPTO.2 closes.

The SDK default backup download strategy remains manual until V-CRYPTO.3.
Synara does not auto-wipe stores or move crypto material through the webview.
