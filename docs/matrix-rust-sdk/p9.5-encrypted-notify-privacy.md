> **Strict acceptance open.** Pure metadata-only privacy policy; no event
> plaintext, OS notification APIs, or cryptographic material.

## Summary

- `CandidateMeta` carries only the `lock_screen_safe_preview` assertion.
- `apply_policy(candidate_meta, room_is_encrypted, app_locked)` returns a
  `PrivacyDecision` with an allow flag, `EncryptionPrivacyMode`, and stable,
  content-free diagnostic reason identifier.
- Locked candidates without a safe generic preview are suppressed.
- Locked candidates with a safe preview are redacted, regardless of encryption.
- Unlocked encrypted-room candidates are sender-only.
- Unlocked unencrypted-room candidates use a redacted preview.
- Marker: `matrix-notification-privacy-p9.5`.

## Privacy invariants

- Candidate metadata contains no title, body, event payload, media, token,
  secret, recovery key, or cryptographic key.
- A lock-screen-safe flag authorizes only a generic redacted preview.
- Diagnostic identifiers are static strings and never interpolate candidate
  data.
- Policy decisions do not implement, request, or inspect event decryption.

## Out of scope

- Matrix encrypted-event decryption or key access
- OS notification and lock-screen APIs
- JS-to-Rust token migration
- Production Tauri commands or dual-backend selection

The product remains on `matrix-js-sdk` until cutover.

## Acceptance

- Unit coverage for encrypted/unlocked, locked/safe, locked/unsafe, and
  unencrypted/unlocked decisions
- Marker registration in `matrix/mod.rs`
- `cargo fmt`, focused tests, and clippy with warnings denied
