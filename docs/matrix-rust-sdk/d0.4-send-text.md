# D0.4 — desktop plain-text send ownership

Status: product-wired desktop slice.

## Ownership

When the desktop host reports a live native Matrix session, the room composer
routes ordinary `m.text` submissions to `matrix_send_text`. That command uses
the same managed `matrix_sdk::Client` that owns login, sync, room list, and
timeline reads. It resolves the joined room and calls `Room::send`; the
composer does not call matrix-js-sdk `sendMessage` after native ownership has
been selected, including on native send failure.

Web builds and desktop sessions without a live native login retain the legacy
JavaScript send path.

## Command contract

`matrix_send_text(room_id, body, reply_to?, txn_id?)` accepts a Matrix room ID,
plain-text body, and optional reply event / caller transaction IDs. Replies
carry an `m.in_reply_to` relation. If a transaction ID is supplied it is passed
to the SDK send future; otherwise the SDK generates one.

The response contains only:

- room ID
- server event ID
- host-local transaction ID
- `sent` status

No access/refresh token, ciphertext, homeserver response body, or crypto
material crosses IPC. Errors use fixed product messages and diagnostic IDs.
The existing generation-stamped `SendQueue` tracks the in-flight attempt and
its sent/failed terminal state locally.

## Residual send paths

This slice intentionally leaves these on the matrix-js-sdk path for later
ownership work:

- attachment and media upload/send, including GIFs and stickers
- reactions
- polls
- non-text composer events such as `/me` emotes and notices

Rich HTML and explicit mention metadata are not part of the native D0.4
contract; native `m.text` sends preserve the plain-text body and emit an empty
`m.mentions` object. Basic replies are supported, while thread-specific
relations remain a later slice.

Encrypted rooms use the SDK's current `Room::send` behavior, but crypto
minimum and encrypted unable-to-decrypt recovery are D0.5 work. D0.4 does not
claim encrypted UTD handling or crypto parity.
